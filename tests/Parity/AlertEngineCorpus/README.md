# Alert Engine Golden Corpus

Machine-checkable form of [docs/alerts/engine-semantics.md](../../../docs/alerts/engine-semantics.md):
the normative behaviour of the leaf/node alert evaluation engine, pinned ahead of its
port to the shared Rust crate (`nocturne-alerts-core`) consumed by both the backend and
Prelude (Android).

Each scenario is a pair of files:

- `<name>.json` — the scenario: alert rules (condition trees as stored in
  `alert_rules.condition_params`) plus a sequence of evaluation ticks, each with an
  explicit `now` and a fully-specified sensor context.
- `<name>.expected.json` — the snapshot: per tick, per rule — root condition truth,
  per-leaf force-eval truths (replay leaf-log semantics), excursion tracker transition
  and state, auto-resolve outcome, and sustained-timer set/clear operations with their
  `(rule, path)` keys.

**Do not edit these files by hand.** They are generated by
`tests/Parity/Nocturne.Alerts.ParityCorpus.Generator` while the C# engine is the
authority:

```bash
# regenerate after a deliberate engine behaviour change
dotnet run --project tests/Parity/Nocturne.Alerts.ParityCorpus.Generator

# verify the committed corpus matches the engine (CI runs this on every push)
dotnet run --project tests/Parity/Nocturne.Alerts.ParityCorpus.Generator -- --check
```

Consumers (in parity-pipeline order):

1. the generator itself (C# engine, authoritative pre-cutover),
2. `crates/nocturne-alerts-core` Rust unit tests (`tests/parity.rs`),
3. the .NET FFI three-way parity suite (`tests/Unit/Nocturne.Alerts.Native.Tests`),
4. Prelude's Kotlin instrumented corpus test (via UniFFI bindings).

After the backend cuts over to the Rust engine, the snapshots become the single
normative spec, regenerated only by the Rust engine.
